# Mac 上的 LLM 原理学习策略

> 适用背景：使用 Apple M3 系列 Mac，通过 nanochat 学习大语言模型原理。当前优先目标是理解代码和计算机制，而不是训练出具备实用能力的聊天模型。
>
> 项目架构、目录职责、依赖与完整学习路线见 [README-SLG.md](README-SLG.md)。本文单独约定学习方法、实验范围和推进方式。

## 一、核心策略

**不把完整训练作为理解代码的前置条件，也不只做静态阅读。采用“具体问题 → 代码追踪 → 手算 → CPU 微型实验 → 回到真实实现”的学习方式。**

需要区分三个层次：

| 层次 | 目标 | 计算资源 |
| --- | --- | --- |
| 阅读、画数据流、手算 | 理解输入输出、公式和设计原因。 | 不需要 GPU。 |
| 小张量、单层网络、一次参数更新 | 观察真实数值、形状、梯度与局部行为。 | 普通 CPU 即可，M3 可以承担。 |
| 较完整的模型训练 | 研究能力形成、泛化、稳定性与规模效应。 | 视模型规模决定是否需要 MPS 或云 GPU。 |

当前优先完成前两个层次。不要求先下载大规模语料、训练分词器或准备可聊天的模型检查点，也不需要先购买云 GPU。

## 二、学习目标与边界

### 2.1 要达到的目标

阅读一段代码后，能够回答：

1. 它解决什么问题？
2. 输入的形状、类型和含义是什么？
3. 每一步计算改变了什么？
4. 输出是什么，后续代码如何使用它？
5. 修改这里会影响什么行为？
6. 如何用一个小例子验证自己的解释？

**学习标准不是“代码看过了”或“训练启动了”，而是能够预测计算行为，再用实验核对。**

### 2.2 暂时不做的事情

- 不直接运行 `runs/speedrun.sh`。
- 不把 `runs/runcpu.sh` 当成必须先完成的入门任务；它仍包含较重的数据准备和训练。
- 不为了讲清一个算子，启动完整数据流水线或完整模型训练。
- 不先研究多卡通信、FP8、Muon 内部算法和自动超参数缩放。
- 不为了让教学例子更简单而直接删除、改写项目中的高级机制。
- 不用微型实验的结果推断真实模型能力或完整训练耗时。

## 三、每次学习的固定流程

### 第一步：只提出一个具体问题

例如：

- token ID 如何变成向量？
- 为什么 Attention 要使用 Q、K、V？
- 因果掩码如何阻止读取未来位置？
- `backward()` 和 `optimizer.step()` 有什么区别？

避免一次讨论“整个 Transformer 怎么工作”。先把大问题拆成能够独立观察的小问题。

### 第二步：只阅读解决这个问题的代码

定位函数和必要的调用位置，阅读相关片段，不按目录逐文件通读。

开始前说明这段代码在完整流程中的位置：

```text
分词 → 输入构造 → 模型前向 → 损失 → 参数更新
                         ↓
                      生成与采样
```

首次接触时，把主干与优化分开。可以暂时不展开优化细节，但要明确它们真实存在，不能把简化解释冒充完整实现。

### 第三步：固定一个具体输入

明确：

- 每个维度的含义。
- 输入是整数 ID、浮点向量、分数还是概率。
- 必要的参数矩阵和初始值。
- 预期输出的形状或行为。

先预测结果，再运行代码，避免只盯着打印结果猜测含义。

### 第四步：手算或逐步追踪

计算量小的地方手算；维度较多的地方画出形状变化。

每一步都区分：

- **形状变化**：例如从 `[B, T]` 变成 `[B, T, C]`。
- **数值变化**：例如归一化或加权求和。
- **语义变化**：例如从 token 身份变成结合上下文的表示。

### 第五步：用 CPU 微型实验验证

实验只保留当前问题所需的计算：

- 使用极小张量和可复现的输入。
- 随机初始化或采样时固定随机种子。
- 仅打印有解释价值的中间结果。
- 用少量断言验证形状、概率归一化、可见性或参数变化。
- 浮点比较使用合理误差，不把近似计算要求为逐位相等。

独立的小型 PyTorch 实验可先不导入整个项目，避免无关的设备检测、内核加载和数据依赖。需要验证项目接口时，再使用真实模块和对应测试。

微型实验应在学习到相应主题时按需编写，不提前搭建完整教学框架。

### 第六步：回到 nanochat 对照

确认教学实验与源码的对应关系：

- 哪些计算直接对应真实代码？
- 哪些细节被简化或省略？
- 当前项目额外加入了哪些机制？
- 实验结论在哪些条件下成立？

最后用几句话解释本节内容，并预测一次输入或参数变化的结果。能够解释且验证一致，再进入下一节。

## 四、推荐课程顺序

以 `nanochat/gpt.py` 的 `GPT.forward()` 作为整体地图，逐步展开内部计算，再连接训练和推理。

| 顺序 | 主题 | 代码入口 | 最小验证 |
| --- | --- | --- | --- |
| 1 | token、Embedding 与基本形状 | `nanochat/tokenizer.py`、`GPT.forward()` 中的词嵌入 | 用一张小的 Embedding 表查出指定 ID 的向量，理解分词与嵌入不是同一步。 |
| 2 | next-token 输入与目标 | `nanochat/dataloader.py` | 对 `[A, B, C, D]` 构造 `[A, B, C]` 和 `[B, C, D]`。 |
| 3 | 单头注意力与因果掩码 | `CausalSelfAttention.forward()`、`nanochat/flash_attention.py` | 手算 Q/K/V、分数、掩码、softmax 和加权求和。 |
| 4 | 多头注意力 | `CausalSelfAttention.forward()` | 追踪头的拆分和合并；确认各维度的含义。 |
| 5 | MLP、残差与归一化 | `MLP.forward()`、`Block.forward()`、`norm()` | 分别观察非线性变换、残差叠加和 RMSNorm 的效果。 |
| 6 | 完整前向与位置编码 | `GPT.forward()`、`apply_rotary_emb()` | 串起数据流，再理解位置信息如何影响 Q/K。 |
| 7 | 交叉熵与一次参数更新 | `GPT.forward()`、`scripts/base_train.py` | 观察目标概率、loss、梯度和更新前后的参数。 |
| 8 | 自回归生成与采样 | `GPT.generate()` | 用固定 logits 比较贪心、temperature 和 top-k；先不要求模型生成有意义的文本。 |
| 9 | SFT 与监督掩码 | `render_conversation()`、`scripts/chat_sft.py` | 对一条短对话标出参与损失的位置。 |
| 10 | KV Cache | `nanochat/engine.py`、`tests/test_engine.py` | 追踪 prefill/decode 的缓存内容、位置和形状。 |

基础完成后，再选择强化学习、评估指标或性能优化。tokenizer 训练算法、完整训练配方和高性能实现不必在第一轮全部深入。

## 五、三个典型学习例子

### 5.1 沿着输入追踪前向传播

教学用输入：

```text
输入 ID：[2, 5, 1]

B = 1：批大小
T = 3：序列长度
C = 4：隐藏维度
V = 8：词表大小
```

追踪数据流：

```text
输入 ID                 [1, 3]
  → 查 Embedding 表     [1, 3, 4]
  → Transformer         [1, 3, 4]
  → 词表投影与分数处理  [1, 3, 8]
  → 取最后位置          [1, 8]
  → 选择下一个 token
```

必须解释清楚：

- Embedding 是根据 ID 查找可学习向量，不是把 ID 数值直接当成词义。
- Transformer 前后形状可以相同，但向量已经结合可见上下文发生变化。
- logits 的最后一维对应词表中的候选 token，logits 本身不是概率。
- 生成下一个 token 时使用最后位置；训练时通常使用多个位置的预测。

这些维度只用于解释机制，**不是当前 nanochat 模型可直接运行的配置**。实际模型还存在头维度、门控输入维度等约束，不能只缩小 `n_embd` 就假设所有路径都成立。

### 5.2 用极小矩阵理解注意力

先使用两个位置、小维度、单个头，完成：

```text
输入 X
  → 线性变换得到 Q、K、V
  → QKᵀ / √d
  → 加入因果掩码
  → 对 key 位置做 softmax
  → 使用权重对 V 加权求和
```

验证四件事：

1. 第一个位置不能关注第二个位置。
2. 每个查询位置对可见 key 的注意力权重之和约为 1。
3. 在权重非零时，改变可见位置的 V 会影响输出。
4. 在完整的因果注意力计算中，改变未来位置的输入不应影响过去位置的输出。

再回到源码认识多头、RoPE、QK Norm、窗口与额外缩放。上述公式是基础机制，不是当前实现的全部细节。

### 5.3 用一次更新理解训练

固定一个极小网络、一条输入和一个目标，记录：

| 时刻 | 观察内容 |
| --- | --- |
| 更新前 | 目标 token 的概率、loss、选定参数的数值。 |
| `backward()` 后 | 参数的梯度；此时通常还没有执行参数更新。 |
| `optimizer.step()` 后 | 参数是否变化，以及重新前向后的概率与 loss。 |

依次理解：

```text
forward：根据当前参数计算
loss：衡量预测与目标的差距
backward：计算梯度
step：根据梯度和优化器状态更新参数
清空梯度：避免非预期的梯度累积
```

在可控的小例子中选择合适的学习率，观察更新方向。**不能将“一次更新后 loss 必须下降”当作所有模型和优化器都保证成立的定律。**

理解这个闭环后再阅读 `base_train.py`，区分核心训练逻辑与数据预取、梯度累积、精度管理、评估和检查点等工程机制。

## 六、Mac 上的实验原则

### 6.1 默认从 CPU 开始

小张量和单次更新通常不需要 MPS。CPU 路径更直接，便于先验证计算逻辑，避免把设备问题混入原理学习。

需要运行 PyTorch 实验时，可使用项目声明的非 CUDA 环境。以下是参考命令，并非已在当前 Mac 上验证：

```bash
# 假设已经安装 uv，在项目根目录执行
uv sync --extra cpu --group dev
source .venv/bin/activate
```

`cpu` extra 表示选择非 CUDA 的 PyTorch 安装来源，并不意味着禁止使用 Apple GPU。

### 6.2 MPS 是后续选项，不是入门门槛

需要稍大规模实验时，再检查：

```bash
python -c "import torch; print('MPS available:', torch.backends.mps.is_available())"
```

`True` 表示当前 PyTorch 环境可使用 MPS，不代表项目的所有算子、精度组合和完整流程都已验证兼容。实际收益也取决于计算规模，小实验使用 GPU 不一定更快。

M3、M3 Pro、M3 Max 的性能与统一内存配置不同。尚未确认具体型号、内存和软件环境前，不承诺模型规模或训练耗时。

### 6.3 何时再考虑云 GPU

当问题从“这一步怎么算”变成下面这些问题时，再评估云 GPU：

- 足量训练后是否形成某种能力？
- 修改模型或数据后，验证集表现是否更好？
- SFT 或强化学习能否在足够样本上改善任务分数？
- 训练吞吐量、显存占用与规模规律是什么？

届时先定义实验假设、基线、预算和停止条件，再租用资源。云端完整训练用于回答规模和效果问题，不能替代局部机制的理解。

## 七、共同学习的推进约定

- 每次围绕一个主题，不一次展开整个文件或整个训练系统。
- 讲解顺序固定为：问题、代码片段、具体输入、计算追踪、最小验证、回到源码。
- 对尚未掌握的概念先补最少背景，不要求先学完全部数学和深度学习课程。
- 区分已从源码确认的事实、教学简化、尚未运行的实验和已验证结果。
- 不用“运行成功”代替解释，也不用“理论上如此”冒充实验验证。
- 只有实际需要时才新增实验代码；不预先创建整套脚本、框架或大规模数据。
- 涉及修改项目代码、安装环境、下载大数据或付费计算时，先明确范围与成本，再执行。

## 八、每节课结束时的检查清单

- [ ] 能用自己的话解释本节解决的问题。
- [ ] 能指出对应的项目函数或代码片段。
- [ ] 能写出关键张量的形状和含义。
- [ ] 能预测一个输入或参数变化会产生什么影响。
- [ ] 有一个小例子或断言可以验证关键结论。
- [ ] 知道教学例子省略了哪些真实实现细节。
- [ ] 知道当前结论不能证明什么。

最终目标是：**面对具体输入，能够解释代码为什么得到这样的输出；面对一处改动，能够判断它会影响什么，并设计小实验验证。**

本文仅约定学习策略，未新增实验脚本，也不代表已完成 Mac 环境检查、测试或训练。微型实验用于理解局部机制，不能替代真实训练的效果、性能和稳定性验证。
